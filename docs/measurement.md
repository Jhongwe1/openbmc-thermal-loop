# 量測方法學（measurement）

> **這份文件決定我的圖能不能被挑戰。**
>
> 差別不在「我畫了圖」——AI 幫任何人都畫得出漂亮的圖。差別在於:
> 別人能不能拿我的原始資料、跑我的指令、得到同一張圖,
> 並且看得出我**沒有**在哪些地方偷懶或造假。
>
> 相關文件:[`plant-model.md`](plant-model.md)(被控對象是什麼)、
> [`env-baseline.md`](env-baseline.md)(在什麼東西上量的)。

## 1. 實驗協定 —— 每個實驗都必須寫齊七欄

| 欄位 | 說明 | 為什麼 |
|---|---|---|
| **假設** | 我預期看到什麼?**寫在跑之前** | 先跑再說「我本來就這樣想」是自我欺騙的標準流程 |
| **自變因** | 我只改了什麼?**必須只有一個** | 同時改兩個,那張圖什麼都證明不了 |
| **控制變因** | 什麼固定住了?seed、plant 參數、setpoint、負載曲線、swampd 版本 hash、映像檔完整檔名 | 「我以為只改了一個」是最容易錯也最容易被抓的一條 |
| **應變因** | 我量什麼?用 [`bench/metrics.py`](../bench/metrics.py) 的定義,不另外發明 | 指標定義只能有一份,否則 README 與圖會對不起來 |
| **重複次數** | **至少 5 個不同 seed,報中位數與範圍** | 跑一次然後截圖不是量測 |
| **原始數據路徑** | `bench/data/expNN_<variant>_seed<K>.csv` | 原始資料是證據,必須進 git |
| **產圖指令** | 一行,別人照打得到同一張圖 | 不能重現的圖等於沒有 |

### 1.1 ★「自變因只有一個」不是用寫的,是用檢查的

`bench/sim` 每次執行都會把**這次生效的完整參數**印到 stderr
(stdout 是純 CSV,不混在一起)。`bench/exp01_sysid.py` 收下五次執行的參數集,
逐項比對,**除了 `seed` 以外有任何一項不同就中止並報錯**。

```
控制變因檢查通過：5 次執行只有 seed 不同
```

> **為什麼要做到這一步:** 「我只改了一個變因」是實驗協定裡最容易講錯的一句話。
> 講錯的人通常不是想騙人,是**真的以為自己只改了一個**。
> 能讓機器檢查的事,就不要靠記憶。

## 2. 指標定義

**一個指標只在 [`bench/metrics.py`](../bench/metrics.py) 定義一次。**
README、本目錄的文件、圖上的標註、CI 斷言全部引用同一個來源。

目前已實作:`t_peak_c`(全程最高感測溫度)、`fan_power_rel`
(穩態 `(rpm/rpm_max)³` 的時間平均)。其餘標在該檔案的總表裡,註明哪一週實作。

> ### ⚠️ 2026-08-09:這份「唯一定義來源」曾經**一個測試都沒有**
>
> 對照組是**當時**的 C++ 那一側:26 個 gtest case、21 個被證明會咬人的 mutation
> (兩邊後來都長大了 —— **2026-08-16 實測:32 個 gtest case、153 個 pytest case、
> 66 個 mutation**)。
> Python 這一側只有 `ruff` —— 而 ruff 只查風格,不查算得對不對。
> **W7 的主要宣稱 `recover_s_ratio` 就是這裡的函式算出來的**,
> 等它寫完再補測試等於讓數字先進 README、測試後到。
>
> 補起來之後:`test/python/test_metrics.py`(接進 `meson test`),外加打在
> `metrics.py` 上的 **18 個** mutation(P 系列;P 系列共 23 個,其餘掃
> `parse_l2.py` / `provenance.py` / `set_die_temp.py`)。
>
> **寫測試順手改掉的一個真隱患:** `fan_power_rel` 的「最後 120 秒」原本是
> **用列數**框的(取樣週期從**前兩列**推),所以
> ① 軌跡只要不是等間隔,視窗長度就錯,而且**不會有任何錯誤訊息**;
> ② 只有一列的軌跡會丟 `IndexError`,訊息看不出原因。
> 改成用時間框之後兩個都消失了 —— 而且**那本來就是這個指標的定義**
> (「最後 120 秒」講的是時間,不是列數)。
> L2 從 BMC 收資料時取樣間隔本來就會抖,這個陷阱留著就是留給 W9。

> **`fan_power_rel` 的物理依據 ——【查】風扇親和定律:**
> 系統阻抗不變時,風量 ∝ 轉速 N、靜壓 ∝ N²、**功率 ∝ N³**。
> 所以**轉速降 10%,功耗降約 27%**(1 − 0.9³ = 0.271)。
> ⚠️【判】它是**模型算出來的相對值,不是量到的瓦數**。
> 講的時候說「相對風扇功耗」,不要說「省了多少瓦」。

## 3. 誠實準則(七條)

違反任何一條,證據等級就從 T2 掉回 T4。

1. **沒量到的不要寫。** 這個 repo 裡出現的每個數字都要指得到一個 CSV 與一張圖。
2. **不要挑最好看的那次跑。** 報中位數與範圍。
3. **不要把模擬講成實測。** 全文一致用「在我的熱模型上」,不要寫「在伺服器上」。
4. **不要外推。** 這是單節點集總參數模型,不能宣稱對多區域熱耦合有效。
5. **限制寫在圖旁邊**,不要只寫在 README 最後。**圖的 caption 就要寫「本圖為模擬結果」。**
6. **記錄版本。** 每張圖的 caption 要有映像檔完整檔名與**產生它的那份資料的 commit**。
7. **不要引用我沒查過的規格細節。**

### 3.1 圖的 caption 三要素

每張圖的 caption 一定含三樣東西:

```
<實驗說明:改了什麼、固定了什麼、幾個 seed、用什麼方法算的>
[Simulation on my own thermal plant - see docs/plant-model.md. Not measured on server hardware.]
image: obmc-phosphor-image-bletchley-20260728025045.static.mtd  |  data commit: <hash>
```

第三行由 [`bench/provenance.py`](../bench/provenance.py) 產生,**每張圖共用同一份實作**
(有測試守著:`test_every_figure_script_uses_the_shared_version_line`)。

> ### ★★ 2026-08-09:那串 hash 從「HEAD」改成「資料的 commit」
>
> **原本記的是產圖當下的 HEAD。那讓一句宣稱變成假的。**
>
> `bench/plot.py` 的 docstring 寫著「任何人 clone 下來執行同一行指令,
> 得到的是同一張圖」。實際上 **HEAD 每個 commit 都在變**,
> 所以同一份資料在不同時間畫出來**逐 byte 不同** —— 差的就是那串 hash。
> 而且 HEAD 常常與那張圖**無關**:修一個 typo 也會讓 caption 變。
>
> **這是真的去 clone 一份下來跑才發現的。**
> 那是這個專案唯一一個「別人會怎麼看到它」的檢查,而我做得太晚。
>
> 改成記「**這張圖的資料**最後一次變動的 commit」之後:
>
> | | 記 HEAD | 記資料的 commit |
> |---|---|---|
> | 資料沒動、隔了 10 個 commit 再畫 | ❌ 不同的檔案 | ✅ **逐 byte 相同** |
> | hash 指向什麼 | 一個可能無關的 commit | **產生這張圖的那一版資料** |
>
> 前置條件量過了:matplotlib 對同一份輸入是**決定性**的(連畫兩次逐 byte 相同)、
> PNG 裡**沒有時間戳**。所以「逐 byte 相同」是一個公平的要求,而不是奢望。
>
> **產圖程式碼刻意不算進那個 hash**(會有自我參照:改 `plot.py` 的那個 commit
> 在圖被畫出來的當下還不存在)。程式碼那一側由
> `test/python/test_figures.py` 守 ——
> **它會重畫一次,與 repo 裡那張逐 byte 比對**,
> 所以「改了產圖程式卻忘了重畫」會讓測試變紅。
>
> ⚠️ 資料有未 commit 的改動時,hash 後面會加 `-dirty`。

### 3.2 ★ 圖上的文字一律英文

不是崇洋。這台機器沒有 CJK 字型,而**就算裝了,「別人 clone 下來跑一次得到同一張圖」
就會依賴他們的字型設定** —— 沒裝的人會拿到一堆豆腐字。
**圖是交付物,交付物不能依賴我本機的環境。** 中文留在 `docs/` 與 `LOG.md`。

### 3.3 ★ 反造假設計清單(每張圖都要過)

| 檢查 | 為什麼 |
|---|---|
| 原始資料**不平滑、不取平均**畫上去 | 平滑過的曲線看不出是不是編的。**看得到雜訊才知道是量出來的** |
| 擬合曲線**疊在**原始資料上 | 分開畫兩張,讀者無法判斷擬合有多貼 |
| **所有重複全畫**,不是只畫最好看的那一條 | 誠實準則第 2 條 |
| **殘差要畫出來**,不是只報一個 RMS | 一個數字看不出「有沒有系統性偏差」 |
| y 軸的範圍要讓**雜訊與量化階梯看得見** | 見 §4.1 踩過的坑 |
| 擬合曲線**只畫在它有定義的區間** | 畫過頭會暗示模型預測了它其實沒描述的東西 |

### exp01 —— 開環系統識別(FOPDT)

| 欄位 | 內容 |
|---|---|
| **假設** | PWM 從 40% 階躍到 60% 後,感測溫度在 θ 秒後開始下降,以時間常數 τ 趨近新穩態。**K 必為負**。兩點法擬出的 τ 會略小於 `τ_die + τ_sense`、θ 會略大於設定的死區,因為 FOPDT 只有一個時間常數而模型有兩個一階環節;**可檢查的不變量是 τ + θ** |
| **自變因** | PWM(唯一) |
| **控制變因** | `power_w` 固定 150 W、`dt` = 0.1 s、階躍時刻 300 s、總長 900 s、plant 參數全部使用預設值。**由程式檢查**(§1.1) |
| **應變因** | 感測溫度序列 → 兩點法算出的 K / τ / θ / 擬合殘差 RMS |
| **重複次數** | 5 個 seed(0~4),報中位數與 min~max |
| **原始數據** | `bench/data/exp01_sysid_seed{0..4}.csv`(各約 500 KB,已進 git) |
| **中繼資料** | `bench/data/exp01_sysid_meta.txt`(含 sim 回報的完整生效參數) |
| **擬合結果** | `bench/data/exp01_fit.txt`(每個 seed 的值 + 中位數 + 範圍) |
| **圖** | `figures/fig1_sysid.png` |
| **重跑** | `python bench/exp01_sysid.py --out bench/data && python bench/plot.py --fig 1` |

**結果(2026-08-07 實測,5 個 seed 的中位數,方括號是 min~max):**

| 量 | 中位數 | 範圍 | 模型設定值 |
|---|---:|---|---|
| **K** | **−0.3147 °C/%PWM** | [−0.3151, −0.3144] | — |
| **τ** | **43.97 s** | [40.25, 44.45] | `τ_die` = 45 |
| **θ** | **7.20 s** | [6.58, 8.84] | `deadTime` = 3 |
| 擬合殘差 RMS | 0.060 °C | [0.056, 0.089] | — |
| **τ + θ** | **50.99 s** | [49.09, 51.59] | `τ_die + τ_sense + θ` = **51.0** |

**兩個交叉驗證(這一段才是這個實驗的價值所在):**

1. **`τ + θ` 守恆。** 單看 τ 會覺得「怎麼比 48 小」,單看 θ 會覺得「怎麼比 3 大」,
   但**兩個一階環節串聯用 FOPDT 擬合,感測器那一段遲滯會被算進 θ 裡**,總和才是不變量。
   實測 50.99 vs 理論 51.0,差 0.02%。
   → **這是「識別方法對不對」的檢驗,而不是「模型對不對」的檢驗。**
     真實系統上我永遠不知道正確答案,所以要先在知道答案的系統上驗方法。
     這一條也有 gtest:`Identify.RecoversKnownTimeConstants`。
2. **殘差落在雜訊底上。** 量測雜訊 σ = 0.05 °C,量化的 RMS 是
   `LSB/√12 = 0.0625/3.464 = 0.018 °C`,兩者獨立所以平方相加開根號 = **0.053 °C**。
   實測殘差 0.056~0.060。
   → **殘差幾乎等於雜訊底,代表 FOPDT 這個形狀沒有留下系統性偏差。**
     剩下那約 0.028 °C 的系統性成分,對 6.35 °C 的總變化量而言是 0.4%。

**已知限制:**

- seed 2 是離群值(τ = 40.25、θ = 8.84、殘差 0.089),範圍的寬度幾乎由它一個決定。
  **照協定報中位數與範圍,不剔除它。** 剔除離群值需要事先定好規則,事後剔除就是挑資料。
- 這是**開環**實驗,量的是被控對象本身,與控制器無關。

### 4.1 ⚠️ Fig 1 第一版踩到的坑

第一版把整段 0~900 s 都畫上去,結果 **0~240 s 那段從 25 °C 爬到 61 °C 的冷機暖機
把 y 軸拉大了五倍**,真正的實驗(6.35 °C 的變化)被壓在圖的上緣。後果是:
**雜訊完全看不見、量化階梯完全看不見、死區只剩一條線** ——
而「看得到雜訊」正是 §3.3 的第一條反造假要求。

定稿的做法:
- x 軸從階躍前 60 s 開始(`t = 240 s`),**並在 caption 明講被略過的是什麼、為什麼**,
  原始 CSV 仍然是完整的 0~900 s。
- 加一個**死區放大鏡**(階躍前後 50 s 的 inset),讓 θ 變成一段看得見的平台。
- 加一個**殘差面板**,讓「有沒有系統性偏差」用眼睛就看得出來。

> **教訓:** 反造假設計不是加註解,是**版面決定**。
> 一張把資料壓成一條線的圖,再誠實的 caption 也救不回來。

### exp02 —— 兩點符號檢查(W5)

| 欄位 | 內容 |
|---|---|
| **假設** | `ec::pid()` 的誤差是 `setpoint − input`。input 是**絕對溫度**時,溫度上升會讓 error 變負,所以要讓風扇需求隨溫度上升,`proportionalCoeff` **必須是負的**。這句話是**從原始碼推出來的,不是量出來的** —— 所以要量。**預期:** `Kp = +500` 時「越熱輸出越低」,`Kp = −500` 時「越熱輸出越高」 |
| **自變因** | `die0` PID 的 `proportionalCoeff`(唯一)。**由程式改設定檔,不手動編輯**,而且 `assert n == 1` 確認只改到一個欄位 |
| **控制變因** | setpoint 65 °C、`outLim` [3000, 15000]、`samplePeriod` 1.0 s、兩個溫度點 55 / 75 °C、每點沉澱 10 s、映像 `…20260728025045`、swampd `0.1+git0+c5e59550d3-r1`、BMC 不重開。**★ 完整生效設定原樣存進 meta 檔** —— 兩份 meta `diff` 起來**只有 `kp=` 與 `proportionalCoeff` 兩行不同**,這就是「單一變因」的機器可驗證版本 |
| **應變因** | `/tmp/pidlog/pidcore.die0` 的 `input` / `error` / `proportionalTerm` / 未箝位輸出 / 箝位後輸出 |
| **重複次數** | **5 次**。⚠️ 這條路徑是**數位、決定性**的,所以報的不是中位數與範圍,是「**5 次逐點完全相同**」—— 那比一個中位數更強。腳本自己會檢查,不同就以非零離開碼失敗 |
| **原始數據** | `bench/data/exp02_signcheck/kp{500,-500}.csv` + 各自的 `*_meta.txt` |
| **重跑** | `./tools/sign_check.sh 500` / `./tools/sign_check.sh -500`(跑完**自動還原** BMC 為 baseline 並驗證 swampd 回到 active) |

**結果(2026-08-09 實測,5 次重複完全相同):**

| Kp | 55 °C(低於 setpoint) | 75 °C(高於 setpoint) | 判讀 |
|---|---:|---:|---|
| **+500** | **5031** | **3000** | ❌ 越熱轉越慢 —— 符號錯 |
| **−500** | 3000 | **4969** | ✅ 越熱轉越快 —— 符號對 |

> **★ 這個實驗真正的收穫不是「符號要負的」,是那兩個 3000。**

#### ★ 這個實驗的四個設計決定(每一個都推翻了計畫的一句話)

**① 負載階躍是 300 W,不是計畫寫的 400 W —— 而且這是算出來的。**

```
可控功率上限 = (setpoint − t_amb) / rth_min = (65 − 25) / 0.12 = 333.3 W
```

超過它,風扇滿速也壓不到 setpoint,**不管控制器多好**。
實測 400 W:三組 λ 的 PWM 全部貼在 100%、`settle_s` 全是 NaN、三條線疊在一起。
300 W 留 10% 餘裕(滿速穩態 61 °C),實測 PWM 峰值 93~96%。

> **「Fig 2 要不飽和、Fig 3 要飽和」是實驗設計,不是巧合。**
> 飽和是 W7 exp07 要量的東西(anti-windup 的前提就是飽和)。

**② 指標只算階躍之後(`t ≥ 300 s`)。**
軌跡從冷機 25 °C 開始,前 100 秒有暖機超調。把它算進 `t_peak_c` /
`overshoot_c`,量到的是「開機行為」而不是「擾動抑制能力」。
**原始 CSV 保留全程**,裁切只發生在算指標時,裁切點記在 meta。

**③ ★ 計畫的驗收標準「λ 越大 → overshoot 越小」是錯的,方向剛好相反。**

| λ | 峰值偏差 (°C) | settle (s) | pwm p-p (%) | reversals/min |
|---|---|---|---|---|
| 0.5τ | **9.94** | 130 | 1.245 | 31.5 |
| 1.0τ | 12.75 | 172 | 0.710 | 31.0 |
| 2.0τ | **17.00** | 250 | 0.382 | 31.0 |

根因:**「超調」在 setpoint 追蹤與擾動抑制中是兩件相反的事。**
setpoint 階躍時高增益會衝過頭;**負載擾動時高增益壓得住偏差**。
這個實驗做的是後者(功耗跳變),所以 λ 越大峰值偏差越大。

⚠️ 計畫的止損表寫「趨勢相反就先檢查係數符號」。**照做會花半天查一個沒錯的東西。**
見 `LOG.md` 2026-08-11。

**④ ★★ `reversals_per_min` 在這個實驗上量不到差異 —— 而這被登記下來了。**

λ 放大把穩態 PWM 抖動的**幅度**降了 **3.26 倍**(`pwm_pp` 1.245 → 0.382),
但**反轉率沒有變**(31.5 → 31.0,而 seed 間的範圍本身就跨 26%)。

在這個雜訊水準下,`reversals_per_min` 量到的是**感測雜訊的時間結構**,
不是控制律 —— 溫度量化階經過 Kp 放大就是 PWM 的抖動幅度,
但方向反轉的**時刻**由雜訊決定。

> **把 `deadband` 從 0.05 調大就能讓三組分開。沒有調。**
> 那樣得到的差異是我選出來的,不是量到的。
> 這條限制寫在 Fig 2 的參數區塊上,不是只寫在這裡(誠實準則第 5 條)。

**同理:`fan_power_rel` 三組相同(差 0.016%)。** 穩態溫度被 setpoint 釘住、
功耗固定 → 熱阻唯一 → 轉速唯一,**與控制器無關**。
計畫把它當成「λ 放大的代價」也是錯的 —— 代價是峰值溫度(高 7.06 °C)。

#### ★ 這個實驗的五個設計決定

**① 兩組都走 `--anti-windup clamp`,自變因只有箝位範圍(偏離計畫)。**
計畫的做法是 `none` vs `clamp` —— 那會**同時改兩個旗標**,而且 `none`
與「夾不到的 clamp」語意不完全等價。改成只動 `--integral-min/max` 之後,
L1 的 A/B 與 L2 的設定檔 diff(也只差 integralLimit 兩行)**完全同構**。

**② 負載 400 W 是刻意超過可控上限 333.3 W(與 exp05 的 300 W 成對)。**
「Fig 2 要不飽和、Fig 3 要飽和」是實驗設計。實測兩組 PWM 在 400 W 窗內
貼頂(≥99.99%)的時間比例都是 0.883 —— 飽和真的發生了,而且兩組一樣。

**③ 沒有第二段階躍就沒有這個實驗。**
飽和期間兩組輸出被同一個 `out_max` 箝住,plant 看到的輸入相同 ——
差異只存在於積分這個內部狀態。900 s 降回 150 W 讓飽和解除,
「溫度已回落、風扇還在全速」才有機會發生,`recover_s` 才有定義。
(`bench/sim` 的 `--power-down-at` 就是為此加的,守門員 mutation B1。)

**④ `recover_s` 只吃「飽和解除後」的視窗,而且實作必須用位置不用標籤。**
軌跡從冷機開始,整段餵進去會命中暖機段。計畫給的實作拿 pandas 的
index **標籤**去餵 `iloc`(**位置**)—— 裁切過的 DataFrame 上輕則
IndexError、重則默默回錯的秒數。守門員:
`test_recover_s_uses_positions_not_index_labels` + mutation **P17**
(P17 植入的就是計畫那版,與 W6 的 P11/P15 同一家族)。

**⑤ ★ 計畫沒預告的現象:open arm 在冷開機段就分家了(反向 windup)。**
下界 −1e6 讓積分在「溫度低於 setpoint」的暖機段往**負向**挖坑,
風扇比 clamp 組晚開、暖機超調更高,於是兩組帶著略不同的狀態進入階躍
(`t_peak` 92.0 vs 90.1 °C)。這不是污染 —— 是**同一個機制在下界側的表現**,
`config/swampd/README.md` 在 W6 就預言過(「下界為什麼是 0 不是負值」)。
Fig 3 刻意從 t=0 畫整段、把它標在圖上,參數區塊誠實寫明
「兩組進入飽和時狀態略有不同」。

   雜訊步幅 ≈ σ√2·Kc ≈ 0.10 %PWM、追這個負載只要 ~0.33 %PWM/s,
   兩個都在掃描範圍之下。**slew 治的是高增益的病;部署整定已經用 λ
   治掉了這個病。** 所以 Fig 5 回答的是取捨空間的另一條邊:
   保留 λ=0.5τ 的抗擾動峰值,用 slew 買聲學,買到多少、付出多少。
2. **方波負載,全週期 240 s。** 單階躍的穩態段只剩雜訊,「跟不上」
   顯不出來;半週期 120 s > 3×閉環時間常數(≈66 s)→ 每個電平段
   都有「追蹤 + 穩態」兩種行為,指標的 tail 視窗(120 s)正好蓋住
   最後一個完整半週期。250 W 而不是 W6 的 300 W:最緊的組落後時
   PWM 峰值更高,300 W 會把它撞進飽和 ——「安靜」就成了飽和的
   假象而不是 slew 的效果(實測 pwm_max 全組 63.9~80.4%,無飽和)。
3. **anti-windup 用 parity 而不是 clamp。** 上游 `ec::pid()` 在
   slew 有設定時每輪回算 `integralTerm = output − P` —— 這個回算
   是被量機制的一部分;`pi.cpp` 通用路徑沒有它。exp05/exp07 用
   clamp 沒問題(slew 全 0,回算不觸發,兩路徑等價)。

**結果(5 seeds 中位數;完整表在圖上與 meta):**

| | 不限 | 0.25 | **0.5 ★選定** | 1.0 | 2.0 | 4~16 |
|---|---|---|---|---|---|---|
| reversals/min | 23.0 | 1.5 | **6.5** | 19.0 | 24.0 | 24.0 |
| t_peak (°C) | 72.2 | 81.9 | **78.4** | 75.1 | 72.6 | 72.1 |
| fan_power_rel | 0.101 | 0.192 | **0.186** | 0.124 | 0.102 | 0.101 |

  按 seed 配對,range 3.0~4.6)**:反轉 23.0 → 6.5 次/分,代價
  峰值 +6.2 °C、相對功耗 +84%。**這是取捨曲線上的一個點,不是最佳解**
  —— 0.25 買到 15.3× 但峰值 +9.8 °C;1.0 只剩 1.2×。
- **與 Fig 2 的對照(這一段是兩張圖合起來的結論):**
  λ 放大壓的是穩態抖動的**幅度**(pwm_pp 3.26×)但不壓**次數**
  (reversals_ratio_lambda ≈ 1);slew 壓的是次數。兩種不同的聲學

  slew 買次數的熱代價相當(+6.2 °C)**但額外付 +84% 相對功耗** ——
  積分在落後期間堆高、回降又被 slewNeg 拖住,平均轉速整段上移。

**量測誠實聲明:**

- `fan_power_rel` 是親和定律 P ∝ N³ 從轉速推算的**相對模型值**,
  不是量到的瓦數。先導還發現它的**符號依負載時間結構而變**:
  週期 120 s 時 slew 收緊反而省功耗(削峰主導)—— 同一個旋鈕,
  負載節奏不同,答案相反。單一週期的掃描不能外推到別的負載。
- `reversals_per_min` 的 deadband = 0.05 %PWM 沿用 W6,未針對本實驗
  調整;小於 deadband 的反轉對這個指標**定義上不可見**。
- slew = 2.0 的中位數(24.0)略高於基準(23.0),配對比 0.92 ——
  幅度在 seed 間變異之內(基準本身 21~24),不宣稱是真實的反彈;
  但它的 seed 帶較寬(見圖),可能與臨界互動有關,未深究。
- 先導試探(λ=2.0τ 死旋鈕、週期 120 s 功耗反向)是設計階段的
  單次/單 seed 快跑,原始檔已被正式掃描覆蓋 —— 它們支撐**設計決策**,
  不進 claims;本節數字全部來自已進 git 的 40 份正式 CSV。

## 5. 量化的宣稱(claims)

`bench/claims.json` 記錄「我對外宣稱的每一個數字」及其來源與容差。
**`value` 一律先填 `null`,等真的量到再填。**
先寫上一個好看的數字再去湊,是造假的起點。

W10 已把它接上 CI(`bench/assert_metrics.py` + `.github/workflows/ci.yml`):
重跑實驗,若任何一個 claim 超出容差就讓 build 失敗。
**意思是「README 上的數字如果不再成立,CI 會告訴我」。**

宣稱分兩類,差別在「CI 上資料哪裡來」(詳見 `bench/assert_metrics.py` docstring):

| 類別 | 實驗 | CI 做什麼 | 斷言的是什麼 |
|---|---|---|---|
| rerun | exp01/05/07/08(L1 模擬) | 重跑模擬 → 重算 → 比對 | 程式碼/參數沒被改到讓數字漂 |
| recompute | exp06/09/10(L2/L3) | 從 git 裡的原始 log 重新推導 → 比對 | **推導**的可重現性(量測重不了 —— CI 沒有 QEMU) |

### 5.1 容差(tolerance_pct)怎麼訂(W10)

計畫的建議公式是「容差 ≈ 2 ×(seed 間相對中位數的最大偏離)」。
**那個公式的前提是 CI 重跑帶隨機性 —— 本 repo 不成立**:重跑是決定性的
(seed 釘死,workflow 另有 CSV 逐 byte 的 `git diff --exit-code`),
重跑雜訊為零,所以容差不是在吸收雜訊。它實際回答的是三層裡的第三層:

1. **決定性層**:重算值應與宣稱值逐位相同。守它的是 byte-diff,不是容差。
2. **環境層**:不同編譯器/函式庫版本的浮點差異。預期 ≪ 1%;
   若 CI 實測超過,按止損表「放寬並記錄」。
   (2026-08-13 預測留檔:本機 WSL Ubuntu 24.04 gcc 13,CI runner 同為
   ubuntu-24.04 → 押 byte-diff 綠;若紅,第一嫌疑是 `-ffp-contract` 的
   FMA 收縮差異,修法是在 meson 裡釘住它,不是放寬容差。)
3. **語意層(實際採用)**:容差 =「數字漂到哪裡,README 那句話就不再成立」。
   例:`recover_s_ratio` 宣稱 13.7×,±15% = [11.7, 15.8] —— README 的講法
   「一個數量級以上」在整個允收區間都成立;`fopdt_tau_s` ±10% —— 斷言的是
   5-seed **中位數**(穩健統計),不是單一 seed;單 seed 偏離可達 8.5%,
   但那是雜訊實現的離散,不是中位數這個統計量的不確定度。

逐欄的特例(理由也寫在各 claim 的 note):

- `fan_power_rel_lambda_spread_pct`:量本身 ≈ 0,相對容差無意義;
  tolerance 1.0 實際上是「spread < 0.032%」的絕對上界。
- `failsafe_detect_s` 0.25:run 間散布 145 ms 是相位採樣偏差(啟動序列
  固定),機制抖動上界 ~1 s / 5.08 s ≈ 0.2,取 0.25 涵蓋其他相位。
- `e2e_inject_to_redfish_s` 0.40:系統級量測受 host 負載影響
  (p95/median = 1.7)。recompute 類在 CI 上其實會逐位重現,
  寬容差保留的是「未來重新量測時仍用同一條斷言」的空間。
