## 0. ★ 為什麼一定要有這個模型

**我一開始做的是開環：** 從外面注入溫度，看風扇怎麼反應
（W2 的 route (a)，W3 的 route (b′)）。**那樣量不到 anti-windup 的效果。**

開環下風扇轉再快溫度也不會降 → 誤差永遠是正的 → 積分永遠在累加 →
PWM 永遠貼在 100%。**你看得到 windup 發生，但看不到 anti-windup 解決了什麼**，
因為 anti-windup 的價值在「**飽和解除之後多快恢復**」，
而開環系統根本不會自己解除飽和。**你畫出來的「階躍響應」只是你手動輸入的形狀。**

```
   swampd (PID) ──PWM──▶ [ 熱模型 ] ──溫度──▶ swampd
        ▲                                        │
        └────────────────────────────────────────┘
```

溫度是 PWM 的函數，PWM 是溫度的函數 —— **這才叫閉環。**

| 這個模型解決什麼 | 為什麼重要 |
|---|---|
| 讓階躍響應有物理意義 | 才量得到超調、穩定時間、震盪 |
| 讓 anti-windup 的效果可見 | 需要「先飽和、後解除」的完整過程 |
| 讓實驗能在 CI 重跑 | 決定性、不需 QEMU、別人 clone 得到同一張圖 |

## 1. 物理

```
              P（功耗, W）
                  │
                  ▼
     ┌──────────────────────────┐
     │  熱容 C（元件 + 散熱片）  │  T_die
     └────────────┬─────────────┘
                  │ 熱阻 Rth（隨氣流變化）
                  ▼
                T_amb（機房進風）
```

風扇這一側：

```
   PWM ──[一階慣性 τ_fan]──▶ RPM ──▶ 氣流 q ──▶ Rth(q)
```

量測這一側（**溫度要走完這三段才會被 BMC 看到**）：

```
   T_die ──[純延遲 θ]──▶ 感測器位置 ──[一階遲滯 τ_sense]──▶ 類比讀值
                                          ──[雜訊 σ]──[量化 LSB]──▶ 數位讀值
```

### 五條方程

| # | 方程 | 意義 |
|:-:|---|---|
| 1 | `rpm ← rpm + (rpm_cmd − rpm)·dt/τ_fan`，`rpm_cmd = 0 if pwm < pwm_min_spin else rpm_max·pwm/100` | 風扇機械慣性 + **起轉死區** |
| 2 | `Rth(q) = Rth_min + (Rth_max − Rth_min)·(1 − q^n)`，`q = rpm/rpm_max` | 強制對流：風越大熱阻越小 |
| 3 | `T_ss = T_amb + P·Rth`，`T_die ← T_die + (T_ss − T_die)·dt/τ_die` | 熱容：一階趨近穩態 |
| 4 | `T_arrived = delay_queue.pop()`，`delay_queue.push(T_die)` | **傳輸死區 θ：純延遲** |
| 5 | `T_sense ← T_sense + (T_arrived − T_sense)·dt/τ_sense` | 感測器熱容造成的遲滯 |

輸出：`reading = round((T_sense + N(0,σ)) / LSB) · LSB`

> ### ⚠️ 方程 4 與 5 是兩件不同的事，順序不能反
>
> **死區（dead time, θ）** 是「訊號整段往後平移」——熱空氣要**先流到**感測器。
> **遲滯（lag, τ）** 是「訊號被低通濾波、變圓」——感測器**自己要熱起來**。
>
> 把死區用一階濾波器近似是很常見的錯誤，結果是 **FOPDT 擬合會把 θ 算進 τ 裡**，
> 於是你調出來的參數在真實系統上會過於激進。
>
> 順序也不能反：物理上先延遲、後遲滯。反過來寫，W4 的兩點法會擬合出不同的 θ 與 τ。
>
> **實測看得見這件事**（`./build/plant_probe 50 150`，pwm 50%、150 W）：
>
> ```
>    t (s)     sensed        die
>      0.0     25.062     25.112
>      1.0     25.000     26.078      ← die 在爬，sensed 完全不動
>      2.0     25.125     26.892
>      3.0     25.000     27.628      ← 到這裡才開始動（θ = 3 s）
>      4.0     25.125     28.318
>      5.0     25.500     28.978
> ```
>
> **前 3 秒 `die` 已經升了 2.6 °C，`sensed` 一動也不動。那就是死區。**

## 2. 參數表

**【判】** = 這是我的工程判斷（order-of-magnitude 合理），不是查證來的事實。
面試講到這些要用「**我的理解是**」開頭。
**【驗】** = 我自己量到的數字。

| 參數 | 值 | 類別 | 理由 |
|---|---|:--:|---|
| `tAmb` | 25 °C | 【判】 | 機房進風的典型值 |
| `P` 基準 / 階躍 | 150 W → 400 W | 【判】 | 一個 CPU 節點的量級 |
| `rthMax`（0 RPM） | 0.35 °C/W | 【判】 | 自然對流。150 W → +52.5 °C，散熱片在無風下的合理量級 |
| `rthMin`（滿速） | 0.12 °C/W | 【判】 | 滿速強制對流。150 W → +18 °C |
| `flowExp` n | 0.8 | 【判】 | 強制對流的經驗指數，文獻常見 0.6~0.8 |
| `tauDie` | 45 s | 【判】 | **散熱片的熱容主導**，不是矽晶片本身（那是毫秒級）。數十秒量級 |
| `tauFan` | 1.5 s | 【判】 | 40 mm 高速風扇的機械慣性 |
| `tauSense` | 3 s | 【判】 | 板載溫感封裝自己的熱容 |
| `deadTime` θ | 3 s | 【判】 | 氣流路徑 + i2c 取樣週期。**這是讓迴路難調的主因** |
| `rpmMax` | 15000 RPM | 【判】 | 伺服器 40 mm 風扇的量級 |
| `pwmMinSpin` | 12 % | 【判】 | 低於此不轉。**真實的非線性**，低負載 hunting 的來源 |
| **`lsb`** | **0.0625 °C** | **【驗】** | ★ **實測**：設 40.000 °C 進 QEMU 的 tmp421，BMC 讀回 **39.938**。那顆晶片的溫度暫存器只給 4 個小數位元 → 1/16 °C |
| `noiseSigma` | 0.05 °C | 【判】 | ADC + 環境擾動 |

### ★ `lsb` 為什麼不照計畫寫的 0.5

計畫範本填 0.5 °C（「常見溫感解析度」）。**但我有真的數字，就用真的。**

**更重要的理由：L1 與 L2 的圖要能直接疊。**
L2 走的是真的 tmp421，量化步階就是 0.0625；如果 L1 模型用 0.5，
兩層的量化雜訊差了八倍，「L1 的結論在 L2 也成立」這句話就沒辦法宣稱。

### ★★ 關鍵設計：`P` 為什麼要階躍到 400 W

**因為要製造飽和。**

```
pwm = 100 %、P = 400 W 時：T_ss = 25 + 400 × 0.12 = 73 °C > setpoint 65 °C
```

**即使風扇開到滿速也降不到目標溫度** → 控制器輸出撞上限 → 誤差持續為正 →
**積分項持續累加 = windup**。

**沒有這一步就沒有 windup，沒有 windup 就沒有 Fig 3。**
Fig 3 是整個專案的招牌，**它的實驗條件是在這張參數表裡決定的**。

W4 會把這個條件寫成一個叫 `SaturationCaseHolds` 的 gtest ——
**那個測試測的不是程式，是「我的實驗設計還有沒有效」。**

## 3. 驗收（2026-08-06 實測）

```bash
meson compile -C build
./build/plant_probe <pwm%> <功率W>
```

| 場景 | 手算 `T_amb + P·Rth` | 模型 300 s 後 | 差 |
|---|---|---|---|
| pwm 0 %、150 W | 25 + 150 × 0.35 = **77.500** | 77.424 | −0.076 |
| pwm 50 %、150 W | 25 + 150 × 0.2179 = **57.685** | 57.639 | −0.046 |
| pwm 100 %、150 W | 25 + 150 × 0.12 = **43.000** | 42.975 | −0.025 |
| **pwm 100 %、400 W** | 25 + 400 × 0.12 = **73.000** | **72.934** | −0.066 | 

**四個都對，而且第四個 72.93 > 65 —— Fig 3 的實驗條件成立。**

> **那個 −0.0x 的差不是 bug，是還沒完全收斂。**
> 一階系統 300 s / τ 45 s ≈ 6.7 個時間常數，理論殘差 e^-6.7 ≈ 0.12 %，
> 對 57.7 °C 就是 0.07 °C。**量級完全吻合。**
> 這種「差多少、為什麼差這麼多」要說得出來，不然就只是「看起來差不多」。

**動態驗收：**

| 檢查 | 預期 | 實測 |
|---|---|---|
| 從 `T_amb` 出發 | 25 °C | 25.06 |
| 前 θ 秒感測值幾乎不動 | 3 s | ✅ 見 §1 的表 |
| 到達 63.2 % 的時間 | ≈ τ_die + τ_sense + θ = 51.0 s | **50.1 s** |
| 風扇轉速 | pwm 50 % → 7500 RPM，τ_fan 1.5 s 內到位 | ✅ t = 5 s 已達 7278 |

> **63.2 % 那一條是 W4 `TimeConstant` 測試的預告。**
> 兩個一階環節串聯不是嚴格相加，所以 50.1 vs 51.0 的 1.8 % 差是預期的。

## 4. 兩個設計約束（這一節比參數表更重要）

### 4.1 `step()` 不做任何 IO

不讀檔、不讀時鐘、不發 D-Bus、不印東西。**只吃輸入、動內部狀態、回傳值。**

**為什麼：** 這是它能同時服務三層的唯一理由。

```
                    ┌──────────────────────────┐
                    │  plant/thermal_plant.cpp │  ← 一份 C++ 程式碼
                    └───────────┬──────────────┘
              ┌─────────────────┼─────────────────┐
              ▼                 ▼                 ▼
        L0 gtest           L1 bench/sim      L2 D-Bus 橋接
      （微秒，CI 內）      （我的 PI）        （真 swampd）
```

一旦 `step()` 裡出現 IO：L0 測不動它（要 mock）、L1 跑不快、
L2 與 L1 變成兩個不同的被控對象。**「L1 的結論在 L2 也成立」就沒辦法宣稱。**

### 4.2 `step()` 與 `sensedAnalog()` 是兩個不同的出口

| 方法 | 回傳什麼 | 給誰用 |
|---|---|---|
| `step(pwm, P)` | 死區 + 遲滯 + **雜訊 + 量化** | **L1**：模型自己模擬整條量測鏈 |
| `sensedAnalog()` | 死區 + 遲滯，**不含雜訊與量化** | **L2**：寫進 QEMU 的 tmp421 |

**為什麼要分開：** L2 那一路上，量化是**真的晶片**做的。
如果 L2 拿 `step()` 的回傳值去注入，量化會發生**兩次** ——
量到的解析度誤差是實際的兩倍，L1 與 L2 的比較就失去意義。

> **這一條是「同一份模型貫穿三層」這個宣稱能不能成立的細節。**
> 不分開也能跑，但兩層的圖疊起來會差一個量化步階，
> 而那個差你會查很久才發現是自己造成的。

## 5. 這個模型**不**宣稱什麼

**誠實邊界（面試一定要主動講，不要等對方問）：**

- ❌ 它不是某台真實伺服器的辨識結果。參數是【判】，不是量出來的。
- ❌ 它是**集總參數**模型：整塊散熱片當成一個溫度點，沒有空間分布。
- ❌ 沒有模擬熱耦合（旁邊的元件互相加熱）、沒有模擬風扇故障、
  沒有模擬進風溫度隨時間變化。
- ❌ `Rth ∝ 1/v^n` 是經驗式，不是從 Nusselt 數推的。

**它宣稱的是：** 一個**在物理上說得通、參數量級合理、行為可重現**的被控對象，
足以讓「控制器在飽和與飽和解除時的行為差異」變成可量測的東西。

> **W4 會做系統識別**：對這個模型跑開環階躍，用兩點法擬出 FOPDT 的 K、τ、θ，
> 再回頭跟這裡填的參數比。**擬出來的 τ 應該接近 τ_die + τ_sense、θ 接近 deadTime**
> —— 那一步是在驗「我的識別方法對不對」，因為這次我**知道正確答案**。
> 真實系統上你永遠不知道正確答案，所以要先在知道答案的系統上驗方法。
