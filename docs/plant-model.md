## 0. ★ 為什麼一定要有這個模型

**我一開始做的是開環：** 從外面注入溫度，看風扇怎麼反應
（W2 的 route (a)，W3 的 route (b′)）。**那樣量不到 anti-windup 的效果。**

開環下風扇轉再快溫度也不會降 → 誤差永遠是正的 → 積分永遠在累加 →
PWM 永遠貼在 100%。**你看得到 windup 發生，但看不到 anti-windup 解決了什麼**，
因為 anti-windup 的價值在「**飽和解除之後多快恢復**」，
而開環系統根本不會自己解除飽和。**你畫出來的「階躍響應」只是你手動輸入的形狀。**

```
   swampd (PID) ──PWM──▶ [ 熱模型 ] ──溫度──▶ swampd
        ▲                                        │
        └────────────────────────────────────────┘
```

溫度是 PWM 的函數，PWM 是溫度的函數 —— **這才叫閉環。**

| 這個模型解決什麼 | 為什麼重要 |
|---|---|
| 讓階躍響應有物理意義 | 才量得到超調、穩定時間、震盪 |
| 讓 anti-windup 的效果可見 | 需要「先飽和、後解除」的完整過程 |
| 讓實驗能在 CI 重跑 | 決定性、不需 QEMU、別人 clone 得到同一張圖 |

## 1. 物理

```
              P（功耗, W）
                  │
                  ▼
     ┌──────────────────────────┐
     │  熱容 C（元件 + 散熱片）  │  T_die
     └────────────┬─────────────┘
                  │ 熱阻 Rth（隨氣流變化）
                  ▼
                T_amb（機房進風）
```

風扇這一側：

```
   PWM ──[一階慣性 τ_fan]──▶ RPM ──▶ 氣流 q ──▶ Rth(q)
```

量測這一側（**溫度要走完這三段才會被 BMC 看到**）：

```
   T_die ──[純延遲 θ]──▶ 感測器位置 ──[一階遲滯 τ_sense]──▶ 類比讀值
                                          ──[雜訊 σ]──[量化 LSB]──▶ 數位讀值
```

### 五條方程

| # | 方程 | 意義 |
|:-:|---|---|
| 1 | `rpm ← rpm + (rpm_cmd − rpm)·dt/τ_fan`，`rpm_cmd = 0 if pwm < pwm_min_spin else rpm_max·pwm/100` | 風扇機械慣性 + **起轉死區** |
| 2 | `Rth(q) = Rth_min + (Rth_max − Rth_min)·(1 − q^n)`，`q = rpm/rpm_max` | 強制對流：風越大熱阻越小 |
| 3 | `T_ss = T_amb + P·Rth`，`T_die ← T_die + (T_ss − T_die)·dt/τ_die` | 熱容：一階趨近穩態 |
| 4 | `T_arrived = delay_queue.pop()`，`delay_queue.push(T_die)` | **傳輸死區 θ：純延遲** |
| 5 | `T_sense ← T_sense + (T_arrived − T_sense)·dt/τ_sense` | 感測器熱容造成的遲滯 |

輸出：`reading = round((T_sense + N(0,σ)) / LSB) · LSB`

> ### ⚠️ 方程 4 與 5 是兩件不同的事，順序不能反
>
> **死區（dead time, θ）** 是「訊號整段往後平移」——熱空氣要**先流到**感測器。
> **遲滯（lag, τ）** 是「訊號被低通濾波、變圓」——感測器**自己要熱起來**。
>
> 把死區用一階濾波器近似是很常見的錯誤，結果是 **FOPDT 擬合會把 θ 算進 τ 裡**，
> 於是你調出來的參數在真實系統上會過於激進。
>
> 順序也不能反：物理上先延遲、後遲滯。反過來寫，W4 的兩點法會擬合出不同的 θ 與 τ。
>
> **實測看得見這件事**（`./build/plant_probe 50 150`，pwm 50%、150 W）：
>
> ```
>    t (s)     sensed        die
>      0.0     25.062     25.112
>      1.0     25.000     26.078      ← die 在爬，sensed 完全不動
>      2.0     25.125     26.892
>      3.0     25.000     27.628      ← 到這裡才開始動（θ = 3 s）
>      4.0     25.125     28.318
>      5.0     25.500     28.978
> ```
>
> **前 3 秒 `die` 已經升了 2.6 °C，`sensed` 一動也不動。那就是死區。**

### ★★ 2.1 注入路徑的傳遞特性（exp04）—— 以及我上一版**推導錯了**的地方

> **這一節記錄一次自我更正。留著它比刪掉它有價值。**

**上一版這份文件寫的是：**

> `lsb = 0.0625 °C`【驗】★ 實測：設 40.000 °C 進 QEMU 的 tmp421，BMC 讀回 **39.938**。
> 那顆晶片的溫度暫存器只給 4 個小數位元 → 1/16 °C

**那個推導不成立，而且它標了【驗】。**

`40.000` 剛好落在 1/16 的格點上（40 = 640/16），**一個純粹的 4 位元小數量化器
應該原封不動回 40.000**。而且單一個點根本分不出「解析度 1/16」與
「解析度 1/32 加上兩格偏移」。**數字是對的，但它是靠巧合對的。**

真正在發生的是**兩件**不同的事，之前被混成一件：

| | 是什麼 | 怎麼量出來的 |
|---|---|---|
| **① 量化** | 讀值只能落在間距 62.5 m°C 的離散階上 | 細掃 42000~42320，讀值只出現 **7 個相異階**，階距在 62 與 63 之間交替（62.5 不是整數）|
| **② −1 LSB 系統性偏壓** | 正好落在格點上的要求值，讀回來**低整整一格** | 7 個格點 × **5 次重複** = 35 個觀測，**全部 −62 m°C，零例外** |

**② 不是量化造成的**（量化對格點上的值應該是恆等映射），是 QEMU setter 的截斷造成的。

#### 根因：三段運算串起來

```
① QEMU setter          hw/sensor/tmp421.c
     s->temperature[i] = (int16_t)((temp * 256 - 128) / 1000) + offset;
                                          ^^^^^ 半個 LSB 的預先扣除，
                                                配上 C 的往 0 截斷，
                                                把值壓到自己那一格的正下方

② 晶片暫存器           同一份檔案的 tmp421_read()
     MSB = temperature >> 8 ；  LSB = temperature & 0xf0
     → driver 拼回來的是 temperature & 0xfff0（只剩 4 個小數位元）

③ Linux driver         drivers/hwmon/tmp421.c 的 temp_from_raw()
     temp = reg & ~0xf
     if (!extended) temp = (s16)temp
     return DIV_ROUND_CLOSEST(temp * 1000, 256)
```

逐步算 42500 m°C：

```
(42500*256 - 128)/1000 = 10879.872  --往 0 截-->  10879
10879 & ~0xf                                   =  10864
DIV_ROUND_CLOSEST(10864*1000, 256) = 42437.5   -->  42438   ✅ 與實測相同
```

這個算式寫成 `tools/set_die_temp.py` 的 `expected_hwmon_mC()`，
**命中 exp04 的 68 個實測點，零誤差**，並由
`test/python/test_injection_model.py` 拿那些 CSV 當回歸測試守著。

> **★ 這一步的意義不是「我算得出來」，是「我把理解變成了會執行的斷言」。**
> `./tools/set_die_temp.py <T> --verify` 會輪詢到 BMC 真的看到預測值為止，
> 否則以非零離開碼失敗。QEMU 或 kernel 哪天換了轉換行為，注入會**大聲失敗**，
> 而不是安靜地給我偏掉的資料。

#### 還有一件更危險的事：注入到可見有延遲

`temp1_input` **不是注入後立刻就變**。Linux driver 的
`tmp421_update_device()` 是 `time_after(jiffies, data->last_updated + (HZ / 2))`
—— **500 ms 的快取窗口**。

實測（`bench/data/exp04_injection/latency.csv`，6 次轉換、25 ms 取樣）：

| 量 | 值 |
|---|---|
| 首次可見延遲 中位數 | **351 ms** |
| 範圍 | **178 ~ 423 ms** |

落在 0~500 ms 之間，與「注入時刻相對快取窗口是均勻分布」一致。

> ⚠️ **對 W6/W7 的殺傷力：** L2 閉環如果從 host 驅動
> 「注入 → 讀 → 算 → 再注入」，整條迴路會**慢一拍**，
> 而那會被誤判成**額外的死區 θ** —— 剛好就是 W4 花一天量出來、
> 還用 `τ+θ` 守恆交叉驗證過的那個量。
> 症狀會出現在 W9 的 L1 vs L2 對照上（「實機比模擬多一個取樣的死區」），
> 然後你會去改模型 —— **改錯地方**。

> ★★ **量測工具比要量的現象慢，會得到「現象不存在」的錯誤結論。**
> 第一版的取樣是「每讀一次開一條新的 ssh」，單次來回約 **0.4 s**，
> 跟 0.5 s 的快取窗口同一個量級 —— 於是**每一次都量不到舊值**，
> 自我檢查回報「快取不存在」。改成一條持久連線上跑迴圈（單次毫秒等級）
> 之後才量得出上面那條延遲曲線。
> **「量不到」與「不存在」是兩件事**，這是這個實驗最值得講的一課。

### ★ `lsb` 為什麼不照計畫寫的 0.5

計畫範本填 0.5 °C（「常見溫感解析度」）。**但我有真的數字，就用真的。**

**更重要的理由：L1 與 L2 的圖要能直接疊。**
L2 走的是真的 tmp421，量化步階就是 0.0625；如果 L1 模型用 0.5，
兩層的量化雜訊差了八倍，「L1 的結論在 L2 也成立」這句話就沒辦法宣稱。

### ★★ 關鍵設計：`P` 為什麼要階躍到 400 W

**因為要製造飽和。**

```
pwm = 100 %、P = 400 W 時：T_ss = 25 + 400 × 0.12 = 73 °C > setpoint 65 °C
```

**即使風扇開到滿速也降不到目標溫度** → 控制器輸出撞上限 → 誤差持續為正 →
**積分項持續累加 = windup**。

**沒有這一步就沒有 windup，沒有 windup 就沒有 Fig 3。**
Fig 3 是整個專案的招牌，**它的實驗條件是在這張參數表裡決定的**。

W4 會把這個條件寫成一個叫 `SaturationCaseHolds` 的 gtest ——
**那個測試測的不是程式，是「我的實驗設計還有沒有效」。**

```bash

./build/plant_probe <pwm%> <功率W>
```

| 場景 | 手算 `T_amb + P·Rth` | 模型 300 s 後 | 差 |
|---|---|---|---|
| pwm 0 %、150 W | 25 + 150 × 0.35 = **77.500** | 77.424 | −0.076 |
| pwm 50 %、150 W | 25 + 150 × 0.2179 = **57.685** | 57.639 | −0.046 |
| pwm 100 %、150 W | 25 + 150 × 0.12 = **43.000** | 42.975 | −0.025 |
| **pwm 100 %、400 W** | 25 + 400 × 0.12 = **73.000** | **72.934** | −0.066 | 

**四個都對，而且第四個 72.93 > 65 —— Fig 3 的實驗條件成立。**

> **那個 −0.0x 的差不是 bug，是還沒完全收斂。**
> 一階系統 300 s / τ 45 s ≈ 6.7 個時間常數，理論殘差 e^-6.7 ≈ 0.12 %，
> 對 57.7 °C 就是 0.07 °C。**量級完全吻合。**
> 這種「差多少、為什麼差這麼多」要說得出來，不然就只是「看起來差不多」。

**動態驗收：**

| 檢查 | 預期 | 實測 |
|---|---|---|
| 從 `T_amb` 出發 | 25 °C | 25.06 |

### 3.2 系統識別交叉驗證（★ 這一節是「驗方法」不是「驗模型」）

用這個 plant 產生開環階躍，再用兩點法（`plant/identify.cpp`）把它擬回 FOPDT，
**跟這裡填的參數對照** —— 因為這次我**知道正確答案**。
真實系統上永遠不知道，所以要先在知道答案的系統上驗方法。

| 量 | 5 seed 中位數 | 範圍 | 這裡設定的 |
|---|---:|---|---|
| K | −0.3147 °C/%PWM | [−0.3151, −0.3144] | — |
| τ | 43.97 s | [40.25, 44.45] | `tauDie` = 45 |
| θ | 7.20 s | [6.58, 8.84] | `deadTime` = 3 |
| **τ + θ** | **50.99 s** | [49.09, 51.59] | **`tauDie + tauSense + deadTime` = 51.0** |

**單看 τ 或單看 θ 都對不上，但 `τ + θ` 守恆到 0.02 %。**
理由：**FOPDT 只有一個時間常數，這個模型有兩個一階環節串聯**
（`tauDie` 與 `tauSense`），多出來的那一段一定會被擠到某個參數裡 ——
兩點法把它擠進了 θ。這與 §1 那個警告是同一件事的反面：
把死區用一階近似，θ 會被算進 τ；把一階遲滯餵給只有一個 τ 的模型，遲滯會被算進 θ。

**第二個交叉驗證：擬合殘差落在雜訊底上。**
`σ = 0.05` 與量化 `LSB/√12 = 0.018` 獨立，合成 **0.053 °C**；實測殘差 0.056~0.060。
→ **FOPDT 這個形狀沒有留下系統性偏差。**

有 gtest 守著：`Identify.RecoversKnownTimeConstants`、
`Identify.SurvivesNoiseAndQuantisation`、`Identify.HandlesRisingResponse`。
圖與完整協定見 `figures/fig1_sysid.png` 與 [`measurement.md`](measurement.md) 的 exp01。

## 4. 兩個設計約束（這一節比參數表更重要）

### 4.1 `step()` 不做任何 IO

不讀檔、不讀時鐘、不發 D-Bus、不印東西。**只吃輸入、動內部狀態、回傳值。**

**為什麼：** 這是它能同時服務三層的唯一理由。

```
                    ┌──────────────────────────┐
                    │  plant/thermal_plant.cpp │  ← 一份 C++ 程式碼
                    └───────────┬──────────────┘
              ┌─────────────────┼─────────────────┐
              ▼                 ▼                 ▼
        L0 gtest           L1 bench/sim      L2 D-Bus 橋接
      （微秒，CI 內）      （我的 PI）        （真 swampd）
```

一旦 `step()` 裡出現 IO：L0 測不動它（要 mock）、L1 跑不快、
L2 與 L1 變成兩個不同的被控對象。**「L1 的結論在 L2 也成立」就沒辦法宣稱。**

### 4.2 `step()` 與 `sensedAnalog()` 是兩個不同的出口

| 方法 | 回傳什麼 | 給誰用 |
|---|---|---|
| `step(pwm, P)` | 死區 + 遲滯 + **雜訊 + 量化** | **L1**：模型自己模擬整條量測鏈 |
| `sensedAnalog()` | 死區 + 遲滯，**不含雜訊與量化** | **L2**：寫進 QEMU 的 tmp421 |

**為什麼要分開：** L2 那一路上，量化是**真的晶片**做的。
如果 L2 拿 `step()` 的回傳值去注入，量化會發生**兩次** ——
量到的解析度誤差是實際的兩倍，L1 與 L2 的比較就失去意義。

> **這一條是「同一份模型貫穿三層」這個宣稱能不能成立的細節。**
> 不分開也能跑，但兩層的圖疊起來會差一個量化步階，
> 而那個差你會查很久才發現是自己造成的。

## 5. 這個模型**不**宣稱什麼

**誠實邊界（面試一定要主動講，不要等對方問）：**

- ❌ 它不是某台真實伺服器的辨識結果。參數是【判】，不是量出來的。
- ❌ 它是**集總參數**模型：整塊散熱片當成一個溫度點，沒有空間分布。
- ❌ 沒有模擬熱耦合（旁邊的元件互相加熱）、沒有模擬風扇故障、
  沒有模擬進風溫度隨時間變化。
- ❌ `Rth ∝ 1/v^n` 是經驗式，不是從 Nusselt 數推的。
  **低轉速區會轉為自然對流主導，指數不同**，這個模型沒有處理那個轉換。
- ❌ 死區時間是**常數**。真實系統的傳輸延遲隨風速變化（風快，熱空氣走得快）。
- ❌ 風扇功耗是用親和定律 `P ∝ N³` 從轉速推算的**相對值**，不是量到的瓦數。

**§3.2 那組識別結果也有邊界：**

- ❌ **`K = −0.3147 °C/%PWM` 只在 PWM 40 %→60 %、150 W 這個工作點附近成立。**
  這個系統是非線性的（`Rth ∝ 1/v^0.8`、外加 `pwmMinSpin` 起轉死區），
  在 20 %→30 % 或 80 %→90 % 量到的 K 不會是同一個數字。
  → **W6 調 PI 係數時要記得：我調的是這個工作點附近的線性化模型。**
- ❌ **`τ + θ` 守恆是「兩個一階環節被一個 FOPDT 吸收」這個結構的性質，
  不是通則。** 三個環節、或有零點的系統不會這樣。
  它在這裡能當驗證工具，只因為我**知道**這個模型長什麼樣。

**它宣稱的是：** 一個**在物理上說得通、參數量級合理、行為可重現**的被控對象，
足以讓「控制器在飽和與飽和解除時的行為差異」變成可量測的東西 ——
而且**每一條性質都有一個測試在守，每個測試都被證明過會紅**（§3.1、§3.3）。
