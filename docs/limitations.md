# 限制與未完成

> 這一份是刻意寫的。作品集最容易被戳破的地方不是「做得少」,
> 而是「宣稱得比做的多」。每一條都是做的過程中遇到、而且說得出
> 「缺了什麼、影響什麼」的;寫不出後半句的不收。
> 五個層面:模型 → 環境 → 控制 → 跨層 → 驗證,
> 最後是每張圖的適用邊界與容差的訂法。

## 模型層面

完整版(含每條參數的【判】/【驗】標記)在
[plant-model.md](plant-model.md) §2 與 §5;這裡列會影響結論解讀的:

- 熱系統是**集總參數一階模型**:整塊散熱片一個溫度節點,沒有空間
  梯度、多熱源、氣流再循環。→ 量到的 τ=43.97 s 是**這個模型的**
  時間常數;真實伺服器是分布參數系統,τ 會隨量測點位置不同。
- 熱阻對氣流用 `Rth ∝ 1/v^0.8` 經驗式,不是從 Nusselt 數推的;
  **低轉速區轉為自然對流主導的轉換沒有建模**。→ K 在低 PWM 區
  不可外插(見下方 Fig 1 邊界)。
- 死區 θ 是**常數**(3 s)。真實系統的傳輸延遲隨風速變化——風快,
  熱空氣走得快。→ 高風速工作點上模型高估延遲,整定偏保守。
- 風扇功耗是親和定律 `P ∝ N³` 從轉速推的**相對值**,不是量到的
  瓦數。→ Fig 5 的「+84% 功耗代價」是模型值,圖上與 claims 裡
  都如此標註;不能拿去跟真實瓦數比。
- `tauDie=45 s`、`pwmMinSpin=12 %`、`noiseSigma=0.05 °C` 等參數
  全是【判】(量級合理的工程判斷),**不是對任何真機的識別結果**。
  唯一的【驗】是量化步階 0.0625 °C(exp04 細掃 QEMU 注入路徑)。
  → 所有絕對數字只在這個模型內有意義;**可遷移的是方法,不是數字**。
- 感測雜訊用高斯白雜訊近似。真實 ADC 有溫度相依偏壓與非白頻譜;
  exp04 量到的 −1 LSB 系統性偏壓是 **QEMU setter 的**行為,
  不能當真晶片的特性。

## 環境層面

- 全部在 QEMU 與本機模擬完成,**我沒有真實的 AST2600 板子**。
  溫度來自 QEMU 的 tmp421 行為模型(`hw/sensor/tmp421.c`),
  注入點在「晶片」層,下游(kernel driver → hwmon → dbus-sensors →
  swampd/bmcweb)是真的軟體路徑——**證明的是路徑,不是熱物理**。
- **I2C bus recovery(9 個 clock pulse)只能講原理,無法驗證**——
  QEMU 模擬不出 SDA 被實體拉低。我驗證的是「感測器讀不到值之後
  的行為」(exp09 failsafe),不是「感測器為什麼讀不到」。
- 感測器逾時是**停止推值**模擬的,不是把 I2C 拔掉;kernel driver
  層的 error path(-EIO、retry)沒有被走到。
- 官方 Robot 測試跑的是 **`QEMU_CI` 清單(20 個生效 include)**,
  不是完整的硬體 CI 清單;失敗案例的數量、根因與判定寫在
  [robot-qemu-ci.md](robot-qemu-ci.md)。**我沒有為了全綠去改測試或環境。**
- 跑 Robot 用的映像**不是 pristine**:`/etc` overlay 帶著本專案的
  entity-manager/swampd 設定(逐案檢查過,失敗與此無關)。
- **端到端延遲(exp10)是在 QEMU 上量的,而且 guest 時鐘本身是
  量測對象級的干擾源**:TCG guest 時鐘以 ~0.81× 速率行走、每
  ~39.7 s 被拉回牆鐘(+7.59 s)。因此只宣稱單一時鐘域的量
  (全程=host 錶、②③=guest 錶),數字用來比較**相對量級與組成
  結構**,不能當真實硬體的絕對值。
- Robot 測試沒有接進本 repo 的 CI——它需要開 QEMU,單輪十幾分鐘,
  超出 CI 的合理預算;取捨是「報告 + 可重跑腳本進 repo」。
- **IPMI:我是「跑過官方 IPMI 測試」,不是「開發過 IPMI 命令」。**
  本映像沒有 netipmid,out-of-band 案例的失敗根因是映像裁剪。
- swampd 的四個 failsafe 相關 build option(`strict-failsafe-pwm`
  等)**沒有驗證過實際行為差異**——那需要重編映像。我讀了
  `meson.options` 知道語意,但沒有實驗證據。

## 控制層面

- **單 zone、單溫感、單風扇群組。** 真實平台有多 zone、zone 間
  氣流耦合。→ 我的結論不含「zone 之間互相搶風」這類系統級效應。
- **內圈(風扇 PID)在我的測試床上實際是開環前饋**:
  `config/swampd/config.baseline.json` 的 fan PID 是
  P=0、I=0、`feedFwdGainCoeff=1/150`(RPM setpoint 線性映射到
  PWM)。→ 原因:我的 plant 沒有建模個別風扇的轉速誤差,回授
  沒有殘差可修。**真實平台的內圈是閉環的**,它吃掉風扇個體差異
  與老化——這一整層價值在我的量測裡不存在。
- L1 模擬是**單迴路**(控制器直接輸出 PWM),只是把取樣週期設
  1 s 對齊外圈;**L1 沒有實作內圈**。內外圈的相位互動只在
  L2/L3 出現(exp06 量到 100 ms / 1000 ms 兩個週期)。
- 沒有實作 stepwise 控制器與 PID 的共存(真實平台常是 stepwise
  管低溫區、PID 管高溫區,zone 內取 max)。swampd 支援,我沒排。
- 沒有 thermal mode profile 切換(`Acoustic`/`Performance`)。
- 沒有處理 host 透過 IPMI OEM 命令餵進來的 margin——**那是真實
  系統很重要的一條輸入**(host 比 BMC 更知道晶片的熱餘裕)。
- **外圈沒有用 D 項**(`derivativeCoeff=0`)。理由是量測鏈有
  σ=0.05 °C 雜訊 + 62.5 m°C 量化,D 項會放大高頻成分——但這是
  教科書論證,**「加了 D 會怎樣」我沒有實驗證據**,那是一個
  沒做的實驗(候選編號 exp11 之後)。

## 驗證層面

- `recover_s` 與 `reversals_per_min` 是**我自己定義的指標,不是
  業界標準**(定義唯一來源:`bench/metrics.py`)。
- **用 `reversals_per_min` 當聲學代理是工程判斷,我沒做過聲壓
  量測驗證這個代理有效**。方向反轉≠可聽噪音;頻率、幅度、
  風扇的機械共振都不在這個指標裡。
- PID 參數是在我的模型上整定的。**換到真實平台一定要重新識別、
  重新整定**;可帶走的是「λ 怎麼選、代價怎麼量」的程序。
- parity 測試把上游釘在 `c5e59550d3`(與 BMC 映像同版,理由在
  `subprojects/*.wrap`)。**上游改了 `ec::pid()`,這個比對就
  過期**——pin 要人為刻意搬,搬的時候分歧案例要重新檢查。
- CI 的斷言分兩級(`bench/assert_metrics.py`):模擬類
  (exp01/05/07/08)**rerun**——CI 重跑實驗再比對;QEMU 類
  (exp06/09/10)**recompute**——CI 只能從 git 裡的原始 log
  重推導指標。→ **QEMU 實驗的「量測」本身沒有自動回歸保護**
  (CI 開不了 QEMU),守住的是「分析程式碼沒有悄悄漂移」。
  哪天換 QEMU 版本重量,數字變了 CI 不會知道,要靠人重跑。
- 官方 Robot 的通過狀態(10 PASS/9 FAIL 有根因)是 **2026-08-12
  那一輪的快照**,上游 test repo 天天在動,不保證對 master 成立。

## 每張圖的適用邊界

宣稱的每個數字、容差與原始 CSV 在 `bench/claims.json`;
這裡是「這張圖在哪個範圍內成立」:

- **Fig 1(sysid)**:K=−0.3147 °C/%PWM **只在 PWM 40→60 %、
  150 W 工作點附近成立**——系統非線性(`Rth ∝ 1/v^0.8` +
  起轉死區),別的工作點是別的 K。`τ+θ` 守恆(51.0 s,0.02 %)
  是「兩個一階環節被一個 FOPDT 吸收」這個結構的性質,**不是通則**。
- **Fig 2(λ 整定)**:量的是**負載擾動抑制**,不是 setpoint
  追蹤——兩者對增益的反應方向相反。λ 放大壓的是抖動**幅度**
  (pwm 峰對峰 3.26×),**次數沒動**(reversals 比值 ≈1,刻意
  登記的無效果結果);三組穩態功耗相同是物理必然,不是發現。
- **Fig 3(anti-windup)**:13.7× 是「integralLimit ±1e6 對
  [0, 100]」兩個**設定**的恢復時間中位數之比(197.2 s → 14.3 s),
  seed 配對計算;上游未修改二進位單趟 12.9× 落在範圍內。
  量化的是**上游既有機制的值**,不是我加了什麼。
- **Fig 4(failsafe)**:5.081 s 的組成是 timeout 設定 5 s +
  逾時檢查騎在外圈 1 Hz 的相位 + 內圈一輪;**run 間散布 145 ms
  遠小於機制抖動上界(~1 s)是採樣偏差**——rig 啟動序列固定,
  每 run 相位幾乎相同,所以容差放 0.25 涵蓋別的相位。
- **Fig 5(slew 掃描)**:掃描基準是 λ=0.5τ,**不是部署採用的
  2.0τ**——slew 治的是高增益的病,在 2.0τ 上整個範圍是死旋鈕
  (八組 reversals 全同)。0.5 %PWM/s 是取捨曲線上選的一個點,
  不是最佳解(0.25 買到 15.3× 但峰值 +9.8 °C)。
- **Fig 6(dts→Redfish 追蹤)**:單顆感測器、單一平台的路徑
  證明(名字換四次、單位換三次);它不宣稱任何熱行為。
